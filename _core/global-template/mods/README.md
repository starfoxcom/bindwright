# Mods — function-hook plugins for `~/.claude`

A mod is a small Claude Code plugin made of **function hooks**: a TypeScript module whose `register(on, options)` function hooks engine events (`session.start`, `prompt.submit`, `tool.call`, `turn.complete`, `ui.render`, …) and reaches the engine through the `$` interface. Mods run inside the Claude Code process, so they can read a command before it runs, add a line to a prompt, draw a band above the prompt, register a slash command or a tool, or wake a session once.

**Requirements:** Claude Code **2.1.287 or newer** (the function-hook API is early access; older builds ignore these folders), and `node` on `PATH` (several mods run a small Node helper for file work the hook sandbox cannot do). The mods run in the terminal CLI and in the Code tab of the Claude Desktop app; both load them the same way (see [Install](#install)).

Every mod is optional and independent, with one exception noted in the table (shared-pc and usage-guard cooperate when both are on). The rows above the prompt replace a status line; see [Rows in place of a status line](#rows-in-place-of-a-status-line).

## The mods

| Mod | What it does | Default |
|---|---|---|
| `session-facts` | Adds one line to every prompt, for the model only: the exact local time, how full the context is measured against the **compaction** window, plan usage per window, the signed-in account's plan name (`| account Max`, from Claude Code's login record, which running sessions follow too; after a `/login` to another account the next line notes `| switched to Max` once), and, while each is still ahead, `usage-guard`'s pause (`| paused until <day time>`) and this session's standing arm (`| armed: resumes <day time>`; an arm at or before the pause's wake reads `armed: resumes with the pause`, since the pause alone does not wake a session that saved no work). A fresh session has no plan figures of its own before its first reply, so its first line borrows the newest ones another session recorded in the last 30 minutes (naming that session's time), and once its own figures arrive, or the line is ten minutes old in a long turn, a newer line rides on the next tool result. Also draws the budgets row above the prompt: context fill to compaction, plan usage per window with the reset time once a window passes the warning level (red at `usage-guard`'s wrap-up level), the `usage-guard` pause beside the plan figures (which then show no reset time, as the pause names the resume; the phone text likewise), and the prompt cache: a countdown in its last minutes naming the cold start (what the next request writes to the cache again if it expires), or the time of Claude Code's own idle compaction when the conversation is big enough for one (200k tokens, or `CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS`); when that time passes by a minute with no compaction and the cache still warm, the mod compacts the conversation itself, once per reply, since the engine stopped doing it in 2.1.293 and does it again only in the terminal from 2.1.299 (its `idleCompact` setting turns that off, and it stays out while auto-compact is off in `/config` or through `DISABLE_AUTO_COMPACT` or `DISABLE_COMPACT`, or idle compaction is off through `"idleCompaction": false` in the settings); and for a quarter hour after a confirmed miss what happened and what it resent, read from the API's own cache counts on the first request after each prompt. The cache's lifetime comes from the session transcript, and the last reply's time is kept in `mods-data/session-facts/<session>.json` so the countdown survives a reload (other sessions' files are swept two days after they were last written). | **Recommended on** |
| `compact-handoff` | Turns compaction into a focused hand-off: your own messages kept word for word (within a budget), a structured hand-off written by the summarizer (doing, where we are, decided, dead ends, read next, reference, live state, owed), and a `recall` tool that searches the full transcript afterwards. A stock summary keeps the gist of messages from two or more compactions back and loses most of their wording; this keeps them word for word, at a few thousand tokens more after a compaction in a long session. | **Recommended on**; mode `on` |
| `ci-watch` | After a `git push` or `gh pr create`, or when the model calls its `watch` tool, watches that PR's checks locally with `gh` (no plan usage while waiting) and wakes the session **once**, only after every check and workflow has finished (a fix pushed mid-run would restart the rest): all passed, failed, or stuck past the time limit. When checks are still pending 15 minutes in, it also reads githubstatus.com (at most every 5 minutes) and, if GitHub reports an open Actions incident, wakes the session once early with the incident's name and shows it on the row. Draws one row per watched PR above the prompt: its progress, a link to it, a button that lists each check, and a stop button. `/ci-watch` lists watches, `/ci-watch stop` clears them. **Research before every PR and every red fix:** a `gh pr create` from the main session is refused until five web lookups on different topics have run since it last opened a PR (a run that prints no new PR's address, such as `--dry-run`, keeps them), and where web tools cannot run, the user opens the PR. Each watch that settles on a head this session pushed or asked to watch is one round (a head someone else pushed, which ci-watch follows without waking the session, is none; a watch that ran out of time is no round, and neither is a red settle where only the review failed, because a review run never got to post its review, which its wake says), kept per PR in `mods-data/ci-watch/rounds.json` and shared by every session on this machine. A round counts red when a check fails (both reviews included), and also when its checks all passed but another push followed instead of the merge. Every red round's wake also asks the session to step back: look up at least five ways others solve the problem, compare them, pick the simplest design that removes the whole class of findings, tell the user, then keep going. That wake also latches the step back on the watch: until five web lookups on different topics (WebSearch, WebFetch or the web-fetch agent) have run, the session's file edits, `git commit` and `git push` are refused, so the fix comes after the research; a green round on the PR also ends it, subagents are not held, and `/ci-watch stop` lifts the hold where web tools cannot run. **The 10th red round is the hard stop:** its wake asks the session to close the PR without merging and rebuild the change from its base branch in a new PR, which starts its own count, and `git commit` and `git push` are refused until the PR is closed. `/ci-watch rounds [<pr>]` shows the count (the PR as a number in the session folder's repo, or as `owner/name#N`). | **Recommended on** |
| `shared-pc` | For several sessions on one machine: one session at a time holds "the seat" for heavy work (builds, full test suites, local CI); the rest wait in a visible line in a band above the prompt. Heavy commands queue by themselves; `/pc` (and the `pc` tool) can hold the seat for one test or command (15 minutes at most; a session that holds again while others wait goes to the back of the line), release it, or ask to go next. Starts no new heavy work while usage-guard has paused sessions. | Opt-in |
| `skill-check` | Checks that a skill's run shows the steps its contract requires. When the turn that ran the skill ends with steps unseen, one follow-up turn names them, asking to do them or say why they do not apply. No contract, no effect. | **Recommended on** |
| `tasks` | Keeps the task list honest: one task in progress at a time, finished work marked done, a list that survives compaction and completion, reminders that name the stale task, and a nudge to make a list after several tool calls with none, a `git commit` held until the list has changed since the last commit, while more than one task is in progress, and while a hold has gone more than 6 hours without being set again (the hold lists every open task with its hold and description, so each is checked against what is true now; the first file edit after a change names the task it belongs to), and, when a turn ends while a task that is not on hold is left and nothing else will wake the session, a refused end of turn once, then a prompt to carry on. Draws its own list (a band and a pane) in place of the built-in panel for the main session. Installing it turns on Claude Code's task tools, which current models hide unless `CLAUDE_CODE_ENABLE_TODO_TOOLS` is `"1"` in `~/.claude/settings.json` `env`; that line stays if the mod is removed. Where Claude Code still offers no `TaskCreate` (a build or model that ignores the line), the mod registers its own `mcp__tasks__taskmod_create`, `taskmod_update`, `taskmod_list` and `taskmod_get` in their place, answered from the same list. | **Recommended on** |
| `usage-guard` | Near a plan usage limit, every session saves its work once (`/close-session`, local only), each project's background work is stopped once by your per-project stop commands, and sessions wait; after the limit resets, each session that saved work gets a prompt to continue it right away, with no plan approval to wait for (never `/start-session`, whose plan would wait for an OK); a session that saved none is only told the limits reset, so two sessions never pick up the same hand-off. The pause gives every session it holds its own resume at the pause's wake, kept apart from an arm set by hand, so a card above the prompt shows it with "Cancel resume (this session)" and "Cancel resume (all sessions)"; `/usage-guard disarm` cancels this session's resume and its own arm alone, and a cancelled resume stays cancelled after a `/clear` or a restart, and `/usage-guard disarm-global` cancels every session's, the arms set by hand included. With two accounts on one computer, a pause belongs to the account it was made on: after a `/login` to an account with room, it ends, and the sessions resume their saved work; a session that also holds an arm set by hand waits instead and shows a card (Dismiss, "Lift it here", "Lift in every session"), or `/usage-guard lift` and `lift-all`, since only the person knows when that work should go on. Plan readings a session took before a switch never start a pause. `/usage-guard arm 5h` (or `week`) has this session alone resume after that reset at any usage level, with no wrap-up and nothing shared; `/usage-guard arm 21:05` resumes it at that time of day instead (24-hour only: `9pm` is refused with its 24-hour spelling), the next time the clock reads it. Add `compact` to compact the session first, and a reason in double quotes (`/usage-guard arm 09:05 "read the trial results"`) for the wake to hand the session; the quotes mark where it starts and ends. The answer gives the wake's full date and how far off it is, and a new arm replaces the standing one. Claude can set the same arm with the `arm` tool when you ask it for a wake-up. A slim line above the prompt shows a standing arm and how much of each plan window is used, with Disarm. The arm survives a `/clear` and a restart: a session started again within `catchUpMinutes` of a missed wake resumes at once, later it only says what it missed. A missed arm whose session stays closed is offered to the next session in the same project (within a day of the wake): a card asks "Resume it here?", or `/usage-guard adopt` (`adopt drop` forgets it) from the phone; one claim keeps it to a single resume. Saved work works the same way: a session that saved its work at the wrap-up but was closed when the reset came is offered to the next session in the same project, with three choices: "Take it here" resumes it in this session, "Keep it there" leaves it for its own session, which resumes it when you open it again (within a week), and "Drop it" forgets it (`/usage-guard adopt`, `adopt keep`, `adopt drop` from the phone). With no open task in the tasks mod's list and no reason, the arm asks to keep it or cancel the resume, and its wake only says it came. `/usage-guard disarm` drops it, and so does a `disarm-global` from any session. The session can compact before a pause too (`compactAbovePercent`). `/usage-guard phone` gives the status as plain text, as a bare `/usage-guard` does over Remote Control. | **Recommended on** |
| `session-info` | One row above the prompt: model and effort, project, and git branch with `*` when it has changes, commits ahead and behind its upstream, and a button that lists the changed files. Rereads git after each turn, after shell commands and on a timer. | **Recommended on** |
| `runners` | One row above the prompt per local CI runner set listed in `runners/hooks/rules.ts` or in `~/.claude/mods-data/runners/runners.json` (the same entries as JSON): on or off (every listed process running), runners online and busy, queued runs and the next scheduled run on the repo's default branch in your local time (all through `gh`), with Start and Stop buttons running your own commands. Stop asks once more while a runner is busy. Draws nothing until you list a runner: `/runners add <name> <program>[,<program>...] [owner/repo]` adds one to the list file and draws its row at once (Start and Stop commands go in the file by hand). `/runners` prints each runner's last reading, or how to add one. An entry with a `wsl` field also shows the WSL disk file's real size on the host (its allocated bytes) against the data in it. While the runners run, the data inside is read at most once a minute and the file every 15 minutes, both right after a start, and the file after a stop; the reading is shared by every session. It flags `trim` (for a sparse disk file) or `compact` when that would give back 10 GB or more, and `+X GB in a week` when the data itself grew by 5 GB or more over the last full week. When the command a Start press runs fails (cannot launch, exits non-zero or runs past 30 seconds), the row says `start failed` until the runners come up. | Opt-in |
| `mods` | `/mods` opens a pane listing every mod in `CLAUDE_CODE_PLUGIN_DIRS`, what each one does (from its `plugin.json`), and the slash commands the plugins add. A command named after a mod is listed under it; the rest (`/pc`, `/task-list`) are listed together below. A mod the current project turned off is marked "off in this project". | **Recommended on** |

"Recommended on" means we suggest installing it with every setup; "opt-in" means install it only when you want what it does. Installing is manual for now (see Install below).

### What each one gains and costs

Setup shows these three columns for every mod it asks about, so turning one on or leaving it off is a choice made knowing both sides.

| Mod | On, you get | On, it costs | Off, you give up |
|---|---|---|---|
| `session-facts` | The exact time, context fill and plan usage in every reply, the budgets row, and idle compaction that still runs where the CLI skips it. | One short line, for the model only, on every prompt, and a row above the prompt. | The assistant guesses the time and how full its context is, and no row shows the plan's limits coming. |
| `compact-handoff` | Your messages kept word for word across compactions, a structured hand-off, and a tool that searches the full transcript. | A few thousand tokens more after each compaction in a long session. | The stock summary, which keeps the gist of older messages and loses their wording. |
| `ci-watch` | Each pushed PR's checks watched at no plan usage, one wake when they finish, research before each PR opens and before the fix of every red round, and one wake when a background shell or subagent the session started writes nothing for 30 minutes without reporting back. | A row above the prompt per watched PR. Opening a PR waits until five web lookups have run since the last one opened, and after every red round file edits, commits and pushes wait for five more; at the 10th, commits and pushes wait until the PR is closed, to be rebuilt in a new one. Needs `gh`. | The session waits on checks itself, spending plan usage, or you tell it when they finish; nothing makes it research before opening a PR or patching again. |
| `shared-pc` | Builds, test suites and local CI from several sessions take turns, so the PC is not starved and timings are not skewed. | A heavy command waits in line while another session holds the seat, and a band shows the line. | Sessions run heavy work at the same time. Worth it only when several sessions work at once. |
| `skill-check` | A step `/start-session` or `/close-session` promised and skipped is caught and named, from the contracts setup writes for each project in `~/.claude/skill-contracts.json`. | Now and then one follow-up turn, which uses plan time. | A skipped step goes unnoticed until it matters. |
| `tasks` | An honest task list that survives compaction and stays current with the code, and unattended work that carries on instead of stopping with tasks left. | Its own band and pane in place of the built-in task panel; a commit waits until the list was updated since the last one, while two tasks are in progress, and while a hold has gone 6 hours without being confirmed; a nudge or a prompt to carry on now and then, which uses a turn; with a task left and nothing to wake the session, the turn's end is refused once. Installing it sets `CLAUDE_CODE_ENABLE_TODO_TOOLS`. | The built-in list, which can go stale, and turns that end with work left until you come back. |
| `usage-guard` | Work saved before a plan limit and resumed by itself after the reset, and wake-ups you can set. | At the wrap-up level (95% by default) every session stops and waits, each project's background work is stopped by your stop commands, and a session that will resume is compacted first when its context is past 35% and the reset is over an hour away. A card and a slim line above the prompt. | A session can hit the limit mid-task, and nothing resumes it after the reset. |
| `session-info` | Model, effort, project, branch and changes at a glance. | A row above the prompt and a git read every 30 seconds. | Only the glance: the same facts are a command away. |
| `runners` | Your local CI runners' state, queue and schedule, with Start and Stop. | A `gh` read every minute while a runner is listed. | Nothing, unless you run local CI runners. |
| `mods` | A pane listing every mod, what it does and its commands. | Nothing while the pane is closed. | The list in one place. |

### Per project or the whole computer

Every installed mod loads in every project, but three can be turned off for one project while every other project keeps them: `ci-watch` (a project with no CI checks has nothing to watch), `tasks` and `skill-check`. `/bindwright:setup project` asks which of them run in a project and writes the answer to that project's personal `.claude/settings.local.json`, which git leaves out:

```json
{ "enabledPlugins": { "ci-watch@inline": false } }
```

The CLI names a mod loaded from `CLAUDE_CODE_PLUGIN_DIRS` `<name>@inline`; a mod switched off this way does not load in that project's sessions from the next session start, and `/mods` marks it "off in this project". The same key in the shared `.claude/settings.json` turns it off for everyone on the project, and the personal file wins where both set it. The other seven act for the whole computer, so they are installed or removed for every project at once (`/bindwright:setup global`): `shared-pc` (a project skipping it would run heavy work without waiting its turn), `usage-guard` (every session wraps up and resumes together at a plan limit), `session-facts` (the state line and the pause notes read it), `compact-handoff`, `session-info`, `runners` and `mods`.

### Options

Options are `userConfig` fields in each mod's `.claude-plugin/plugin.json`: those are the defaults. Each mod keeps the values you change in a file of its own, `mods-data/<mod>/settings.json`, over those defaults. Change them in the mod's settings pane, `/<mod> settings` (`/task-list settings` for `tasks`), which edits them in the terminal and the Desktop app alike, or with `/<mod> set <name> <value>` from the phone (`/<mod> set` alone lists them). The file is read at each session's start and once a minute after its first tool call or command, so every running session picks a change up within a minute; a new check interval takes over at the next tick of the old one. The Desktop app lists no mod rows in `/config`, so each mod hides its rows there; a value set in `/config` or in `~/.claude/settings.json` under `pluginConfigs.<mod>.options` before still counts until the file sets that field.

| Mod | Option | Default | Meaning |
|---|---|---|---|
| `ci-watch` | `pollSeconds` | `30` | How often the PR checks are read with `gh`. |
| `ci-watch` | `timeoutMinutes` | `60` | A watch still pending after this long wakes the session with what is stuck. |
| `compact-handoff` | `mode` | `on` | `off`: stock compaction. `shadow`: stock compaction plus the hand-off written beside it for comparison (double work on every compaction; use only for A/B runs). `on`: the hand-off replaces the stock summary. |
| `tasks` | `nudgeAfterTools` | `3` | Tool calls in one turn with no task list before the model is asked to make one. `0` turns the nudge off. |
| `tasks` | `keepGoing` | `true` | When a turn ends with an open task that is not on hold (nor waiting on another open task), and no CI watch or plan-limit pause will wake the session (nor was such a pause's automatic resume cancelled before its reset), the turn's end is refused once so the work goes on, and the model is prompted a few seconds later to carry on. A CI watch counts only while ci-watch still polls it (a poll in the last 10 minutes, or three poll intervals when it polls slower), and a CI wake that has not come is looked at again every 5 minutes while the session stays idle, so one that never arrives cannot hold the session idle; any new turn cancels that look, also one a reloaded copy of the mod sees. Never after an interrupted turn; stops after two prompts in a row that change nothing on the list, until the next prompt of your own. |
| `usage-guard` | `wrapUpAt` | `95` | Percentage of any plan window (5-hour, weekly) at which sessions wrap up. |
| `usage-guard` | `wakeDelayMinutes` | `2` | How long after the reset sessions resume. |
| `usage-guard` | `compactAbovePercent` | `35` | A session that will resume on its own compacts after its wrap-up when its context is above this share and the reset is more than an hour away. `0` turns it off. |
| `usage-guard` | `catchUpMinutes` | `30` | A session armed to resume that was closed at its wake resumes when it starts again within this many minutes of the wake; later, it only says what it missed. `0` never catches up. |
| `session-facts` | `planWarnAt` | `75` | Plan usage (%) at which a window turns yellow and shows when it resets; it turns red at `usage-guard`'s `wrapUpAt`. |
| `session-facts` | `cacheWarnMinutes` | `10` | The prompt-cache countdown shows once this few minutes are left. |
| `session-facts` | `cacheTtlMinutes` | `60` | The prompt-cache lifetime to assume until it is read from the session transcript after each reply (the API records which lifetime each cache write used: 60 minutes on a plan within its included usage, 5 past it or on an API key), and whenever the transcript cannot be read. In that fallback, a miss between 5 minutes and this lifetime switches the countdown to 5 minutes until a warm request outlives them. |
| `session-info` | `refreshSeconds` | `30` | How often git is reread between turns, to catch a branch switch or an edit made outside the session. `0` rereads only after turns and shell commands. |
| `session-info` | `maxFiles` | `8` | How many changed files the expanded row lists before it says how many more. |
| `runners` | `checkSeconds` | `60` | How often processes, runners, queued runs and schedules are read (schedules at most once an hour). |

`shared-pc` and `skill-check` have no options. Three mods keep a user-editable list in code instead, because the entries are regular expressions and argv lists:

- `shared-pc/hooks/rules.ts`: what counts as heavy work. Global light and heavy lists ship filled in; `projects` ships empty, with a commented example of a per-project entry.
- `usage-guard/hooks/rules.ts`: `STOP_COMMANDS`, the commands that stop a project's background work at wrap-up. Ships empty, with a commented example.
- `runners/hooks/rules.ts`: `RUNNERS`, each runner set's label, process names, repo, and Start and Stop commands. Ships empty, with a commented example.

`/bindwright:update` brings each list current like the mod's other files (its step 5 has the rule), with one exception: on a mod installed before Bindwright kept an install record, the list is kept either way, and the newer shipped copy goes beside it as `rules.ts.new`.

`skill-check` reads its contracts from `~/.claude/skill-contracts.json`, keyed by project folder name. `/bindwright:setup` writes each project's key from `skill-check/skill-contracts.example.json`, keeping only the steps of the features that project turned on, and `/bindwright:update` refreshes it when the session skills change. A project folder that is renamed needs a setup or update run to move its key.

## Install

1. Copy the mod folders you want to `~/.claude/mods/<mod>/` (keep each folder whole).
2. List each one in `~/.claude/settings.json` under `env.CLAUDE_CODE_PLUGIN_DIRS`, as absolute paths (`~` is allowed) joined by the platform's path-list separator:

   ```json
   {
     "env": {
       "CLAUDE_CODE_PLUGIN_DIRS": "C:/Users/<you>/.claude/mods/ci-watch;C:/Users/<you>/.claude/mods/session-facts"
     }
   }
   ```

   With `tasks`, add `"CLAUDE_CODE_ENABLE_TODO_TOOLS": "1"` to the same `env` block: the mod answers Claude Code's task tools, which current models hide without it.

   On Windows the separator is `;` (verified). On macOS and Linux it is `:` (`~/.claude/mods/ci-watch:~/.claude/mods/session-facts`), per the CLI's plugin reference; not yet verified on those systems.

   The CLI draws the rows above the prompt top-down in this list's order, so list the most-read rows last, nearest the prompt: `shared-pc`, `runners`, `usage-guard`, `ci-watch`, `tasks`, `session-info`, `session-facts`, then the mods with no row (`compact-handoff`, `skill-check`, `mods`). `/bindwright:setup` lists them in this order whatever order you pick them in.
3. **Fully restart** Claude Code. The variable is read at start, so a new entry needs a restart. Editing a mod that is already loaded reloads it in running terminal sessions when one of its files is saved.
4. **Desktop app:** it reads the same `~/.claude/settings.json` and its `env` block, so steps 1 to 3 cover it. Keep the variables in that file: on Windows the app also inherits user and system environment variables but never reads a PowerShell profile. The mods run only in **local** Desktop sessions; plugins are not loaded in WSL or cloud sessions. Desktop sessions are not interactive terminal sessions, and the CLI watches mod folders by default only in those, so in Desktop an edited mod loads at the next session start. To reload on save there too, add `"CLAUDE_CODE_PLUGIN_DIR_WATCH": "1"` to the same `env` block; it is optional and only matters while you edit mods. An older Desktop build that places no panes leaves the `tasks` list pane unopened; its band still draws.
5. For `skill-check` without setup: build `~/.claude/skill-contracts.json` from `skill-check/skill-contracts.example.json` as its `_note` says, one key per project.

Load each mod once. A folder enabled for hot reload elsewhere (a development copy) loads again on restart, so remove a development copy once the mod is installed.

## Where data lives

Each mod keeps its files under `~/.claude/mods-data/<mod>/` (or under `$CLAUDE_CONFIG_DIR/mods-data/` when that is set), with hard caps and its own cleanup:

| Mod | Files |
|---|---|
| `compact-handoff` | hand-off files: one per session in `on` mode, plus `<session>-precompute.md` when the engine writes a summary ahead of time; newest 20, at most 14 days, in `shadow` mode |
| `ci-watch` | `<session>.json` (the watches) and `<session>.owner` (which loaded copy of the mod polls); a settled watch stays until the PR is merged or closed, or the user stops it (from an hour after the session's push to it, it checks the PR every 10 minutes, and a new head pushed by someone else updates the row without waking the session); another session's two files are swept two days after it last wrote them, by `scripts/sweep.cjs`; `settings.json` (its settings) and `rounds.json` (each PR's fix rounds: one per settled watch of a pushed head, except one whose only failure is a review run that never got to post its review; a reset empties the PR's list) are never swept |
| `shared-pc` | the seat, line and requests, changed only through `bin/pcctl.cjs` under a lock |
| `tasks` | `<session>.json`, the task list mirror (50 tasks kept), `<session>.alive`, stamped each minute while the session runs, and `<session>.owner` (which loaded copy of the mod saw the session's last turn); another session's three files are swept 14 days after it last wrote them, by `scripts/sweep.cjs`, or after 7 days once the list has nothing left to carry over (handed over to a later session, or every task done or dropped) and its session no longer stamps; an alive stamp or owner file with no list goes after 7 days too; `settings.json` (its settings) is never swept |
| `usage-guard` | `pause.json` (the shared pause), `card.json` (the card every session draws), `claims/` (one empty folder per session and per project per pause, so each wraps up and each project stops once; swept after 14 days), `settings.json` (its settings, written by its pane and `/usage-guard set`), `arms/<session>.json` (a session's standing arm, kept for a restart; `null` once disarmed or run), `fence.json` (per plan limit, the reset of a window that ended early, kept per account when the pause knew one, so an older reading of it never starts a pause; never swept, since an entry stops mattering once its reset passes). `session-facts` reads `pause.json` and this session's `arms/<session>.json` for its prompt line, so a change to either format reaches it too |
| `runners` | `runners.json` (optional): your own runner list, read at session start. The last WSL disk reading lives in the mod's own store (`disk:<name>`), shared by every session, with the session's own copy as the fallback |
| `session-facts` | `<session>.json`: the last reply's time, the prompt-cache lifetime and the last cache check, so the countdown survives a reload, and `<session>.compact.json`, the time its last compaction started. Another session's two files are swept two days after it last wrote them, by `scripts/sweep.cjs`. `plan.json`: the newest plan figures any session recorded, for a fresh session's first line; it and `settings.json` (its settings) are never swept |

## Rows in place of a status line

Four mods each draw one row above the prompt: `session-info` (the session), `ci-watch` (CI), `runners` (local runners) and `session-facts` (budgets). Together they show what a command status line would, with buttons and details a status line cannot have, and they draw in the terminal and in the Desktop app alike; the Desktop app does not draw a command status line. These templates ship no status line any more. If `~/.claude/settings.json` still has a `statusLine` block from an older setup, remove it once the rows are installed, so the terminal does not show the same facts twice. The older `statusline.js` left files under `~/.claude/mods-data/statusline/`, which can be deleted. Its per-session window files in `~/.claude/mods-data/session-facts/` are swept by `session-facts` itself after two days; keep that folder, it holds the mod's own files now.

## Test and validate

From the folder that holds the mods:

```bash
claude plugin validate <mod>   # reads the manifest and hooks module as the engine will; lists hooks, calls and env reads
claude plugin test <mod>       # runs every *.test.ts / *.test.tsx under the mod against the engine
node --test shared-pc/test-helper/pcctl.spec.cjs   # shared-pc's Node helper
node --test compact-handoff/test-helper/helper.spec.cjs   # compact-handoff's Node helper
node --test ci-watch/test-helper/sweep.spec.cjs   # ci-watch's data-folder sweep
node --test tasks/test-helper/sweep.spec.cjs   # tasks' data-folder sweep
node --test session-facts/test-helper/sweep.spec.cjs   # session-facts' data-folder sweep
```

Validation reports one warning per mod (no `author` field); that is expected.

### Editor typings

Each mod's `tsconfig.json` extends `./.claude-plugin/types/tsconfig.json`. That folder is **generated by the engine**, not shipped: every time Claude Code loads the mod from a folder you own (a `CLAUDE_CODE_PLUGIN_DIRS` entry, `claude --plugin-dir <mod>`, or a hot-reloaded development folder), it writes `.claude-plugin/types/` with the API (`claude-code/index.d.ts`), this build's built-in tools, the MCP tools connected at the last reload, and a `tsconfig.json`; it also writes a `.gitignore` there that ignores the whole folder. There is no command to run, and neither `claude plugin validate` nor `claude plugin test` needs it. After the first load, `tsc -p <mod>` type-checks the mod. The `types/index.d.ts` some mods ship is different: it is the mod's own contract for the values it keeps in `$.state`, named in `plugin.json` under `"types"`.

## Writing or changing a mod

Lessons from building these, for the current function-hook API:

- **One hooks module per plugin.** `hooks/hooks.json` names a single entry file; split code by importing into it. `$` never crosses an import: a function that takes `$` must live in the file that calls it, as a top-level declaration, and no parameter may share a name with such a function (the validator refuses it).
- **One hook per event**, unless the later hooks carry a matcher: `on('session.start', { isInteractive: true }, …)` can sit beside an unmatched `session.start` hook.
- **Hot reload watches only the entry file.** After editing a file it imports, also change the entry file, or running sessions keep the old code. A session in the middle of a turn keeps the old code until that turn ends. A change to `CLAUDE_CODE_PLUGIN_DIRS` still needs a full restart.
- **Set up lazily.** A hot reload starts the module's own variables over but does not re-run `session.start` in a running session, so do first-use setup on the first event that needs it too.
- **No missing folders, no deletes.** `$.fs.write` creates no parent folders and the sandbox has no delete; do both through a short Node helper run with `$.process.run`.
- **Render hooks are pure.** Writing state from `ui.render` is refused and the hook is skipped; start timers and fill state from another event.
- **Name clashes:** a variable named `h` shadows the JSX factory ("h is not a function"), and the validator does not catch it.
- **Budget:** a hook has 10 seconds. `$.clock.sleep` counts against it; waiting on `$` calls does not, but a slow `$.process.spawn` inside `tool.call` still holds the command up.
- **Drawing:** a card positioned absolutely above the prompt band is clipped; draw cards inside the band. Build every element through `$.ui.resolve(e)` and keep to the elements both surfaces have (`Box`, `Text`, `Button` and the like; `Raster` and `Image` are terminal-only), and run each mounting test over `['terminal', 'desktop'] as const` so a Desktop break shows in `claude plugin test`. Every `AbovePrompt` hook calls `next(e)` and keeps its own tree, so cards from several mods stack.
- **Notifications:** do not rely on `$.ui.toast` (gone in seconds, no styling), `$.audio.play` (silent in some terminals) or OS notifications (may be off). Anything a person must see is a card in the band that stays until dismissed or answered. Colors: yellow when the person must or may act, blue for information, green for good news, red for an error.
- **Waking a session:** `$.session.append` notes do not wake an idle session; `$.prompt.submit` does, for one turn. Wake once per event.
- **Tests** (`import { test, expect, mock } from 'claude-code/testing'`): `$` in a test has no real file system (hook `fs.read` / `fs.write` yourself; paths arrive with Windows backslashes); there is no `session.append`; `op` events answer `{ value }`; call `$.session.start({ cwd })` and `mock.clock(on)` before mounting a band; a hook's refusal reaches the test's `$.tool.call` as `{ isError, text }`. A `key` on a `Text` fails validation (the engine draws its own component), so key a `Box`; mount a pane with `requestId: <pane id>` and the pane props. The mod under test loads its own copy of its modules, so a test cannot change the mod's behaviour by mutating an imported value; test such tables through an exported pure function instead.
- **Settings pane:** copy `ci-watch/hooks/settings.tsx` (not `usage-guard`'s, which keeps its own settings file), change its `PLUGIN`, `TITLE` and the atom's literal plugin name (the engine reads state names only from literals), call its `register` from the entry module, and open `SETTINGS_PANE` from the mod's command. It reads the mod's rows from `$.config.list()` on every draw and writes through `$.config.set`, so `/config` stays the one store. In tests, answer `config.list` with `on('config.list', () => ({ value: rows }))`, capture writes with a `config.set` hook, mount the pane once and type with `ui.input({ key, text })`.
- **Keep it light:** hard caps on every file a mod writes, cleanup of old files, and injected text that scales to the context window.
