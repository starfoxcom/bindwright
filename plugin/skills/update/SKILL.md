# /bindwright:update

This skill rebuilds the repo's Bindwright files from the answers saved at setup, with today's templates, and merges each one three ways: the file as the last setup or update wrote it, the repo's copy, and the new text. Edits the repo made survive; a file where both sides changed the same lines is left alone for the user to settle. Nothing is committed.

## 1. Check the repo

- Find the repo root with `git rev-parse --show-toplevel`.
- If `.bindwright/pristine.json` or `.bindwright/project.json` is missing, this repo was not set up with Bindwright: tell the user to run `/bindwright:setup` instead, and stop.
- If `git status --porcelain` shows uncommitted changes, say so and ask whether to continue. On a clean tree the update reads as one diff and is undone with `git restore`.
- If `.bindwright/incoming/` already holds files, an earlier setup or update left them unsettled. Say so; step 3 goes through them with the new ones.

## 2. Run the update

Bring the plugins current first. Run `claude plugin list --json` and, for each plugin id ending in `@wrights` (`bindwright@wrights`, `findwright@wrights`), take the install that applies here: the one whose `projectPath` is this repo root, otherwise the one whose `scope` is `user` or `managed`; never one whose `projectPath` names another folder. An install whose scope is `managed` is updated by whoever administers the computer: name it and leave it out of what follows. When none is left, skip this paragraph: a Bindwright installed from another marketplace, such as the plugin directory, updates through that one. Otherwise run `claude plugin marketplace update wrights`, and compare each one's installed version with the `version` its entry under `plugins` holds in `<installLocation>/.claude-plugin/marketplace.json`, where `<installLocation>` is the one `claude plugin marketplace list --json` shows for `wrights`: the marketplace's copy that command just refreshed, wherever Claude Code keeps its files. When any has a newer version, name each with both versions and ask once: "Update them now?", with "Yes" first. On a yes, run `claude plugin update <id> --scope <that install's scope>` for each. When one fails, show its last line and treat that plugin as not moved. When `bindwright@wrights` moved, say that this run is still the old version's: ask the user to type `/reload-plugins` (or restart Claude Code), then `/bindwright:update` again, and stop, since the repo is untouched so far. When only `findwright@wrights` moved, say so and go on: the FindWright paragraph below reads its new install. On a no, when none is newer, or when the marketplace cannot be reached (say so in one line), go on.

Find the helper and pick the engine as setup's step 0 does (`${CLAUDE_PLUGIN_ROOT}/skills/setup/SKILL.md`), installing the helper when it is missing or holds another version than the plugin, as that step does, without a question, then taking out a FindWright copy from an older Bindwright as step 0's paragraph of that name says. With neither, tell the user the update needs Node 18 or later, or Python 3.8 or later, and stop.

FindWright's own parts come along in the same run, so a user never needs `/findwright:update` too. When `claude plugin list --json` shows a `findwright@wrights` install that applies here, picked by the rule above, take its `installPath` and follow `<installPath>/skills/update/SKILL.md`, reading its `${CLAUDE_PLUGIN_ROOT}` as that `installPath`: FindWright's update decides for itself what is behind, and says so in one line when nothing is. When it stops on a failure, say what failed and go on with this update, since Bindwright's files do not need FindWright. Without FindWright installed, say nothing about it.

When that same check found a `@wrights` install that applies here, and the engine's `--settings <repo root>` shows no `plugin-auto-update` entry under `extras`, this computer was set up before plugin auto-update came on by default. Turn it on as setup's step 7 does (`${CLAUDE_PLUGIN_ROOT}/skills/setup/SKILL.md`), with `home.py plugin-auto-update on` and the `--repo` that step names, naming any `blocked_by`; when it is skipped there, skip it here too. Otherwise save `{"extras": {"plugin-auto-update": true}}` with `--remember <repo root> --layer personal`. Say in one line that new wrights plugin versions now arrive by themselves, and that `/bindwright:setup global` turns that off. A saved `false` is the user's no: leave it.

First say what the releases changed: run the engine with `--releases-since <repo root>`. It reads only the plugin's own changelog, never the repo's `CHANGELOG.md`, and prints `{"from": "<bound version>", "to": "<plugin version>", "releases": [{"version", "date", "text"}, ...]}`, newest first. When `releases` holds any, open with a plain summary of each release in the range, newest first and a few short lines each: what is new, what changed and what was fixed, then anything the user may want to act on, such as a new setup answer to consider or a behaviour that now works differently. When it holds an `unavailable` reason, say in one line that the summary is not available and why, and go on.

When `.bindwright/project.json` holds no `versioning` under `advanced`, the repo was set up before setup asked how releases are numbered. Ask it now, as setup's "How releases are numbered" step says (`${CLAUDE_PLUGIN_ROOT}/skills/setup/SKILL.md`, step 3): find the numbering the project uses, then offer to enforce it, or recommend one by what the project is. Write the answer into `advanced` in `.bindwright/project.json` (`"versioning"`, and `"versionFormat"` for calendar versions, `null` otherwise) before the update runs, so it writes the check; a no saves `"versioning": "none"`, so later updates do not ask again.

When `advanced.localOnly` is true in `.bindwright/project.json`, first refresh the exclude list: run the engine with `--local-exclude <repo root>`, passing that file on standard input, so a file the new version adds for the assistant stays out of commits from its first write. Name any `tracked` path it prints, as setup does.

Run it with `--update <repo root>`. It prints one line of JSON:

- `{"error": "..."}`: show the message and stop; nothing was written. Unless it is the symbolic-link message below, offer `/bindwright:report`. A message starting `Refusing to write through a symbolic link` names repo files that are links: the update never writes through one. Offer to list each in `.bindwright/owned`, so later updates leave it alone, or to replace the link with a plain file, then run the update again.
- Otherwise, lists of repo paths by what happened to each file:

| List | What happened | What the user does |
|---|---|---|
| `updated` | The repo never changed the file; it now has the new text | Nothing |
| `merged` | The repo's edits and the template's changes touched different lines; both are in | Read the diff |
| `added` | New in the templates; written in place | Nothing, beyond step 4 |
| `staged` | New in the templates, but the repo already has a file there; the new text is at `.bindwright/incoming/<path>` | Merge it (step 3) |
| `conflict` | Both sides changed the same lines, or the merge would lose a kept section; the repo's copy is untouched and the merge, with all three versions at each clash, is at `.bindwright/incoming/<path>` | Settle it (step 3) |
| `renamed` | Pairs of `[old path, new path]`: the templates moved the file, so its copy, the repo's edits included, now sits at the new path (and in the list above that says how it merged), and the old file is gone | Nothing, beyond what that list asks |
| `removed` | The templates dropped a file the repo never changed | Say whether to delete it |
| `removed_edited` | The templates dropped a file the repo changed; it stays | Nothing, or delete it by hand |
| `deleted` | The repo deleted a file setup wrote; it stays deleted | Nothing |
| `owned` | Listed in `.bindwright/owned`; never touched | Nothing, beyond step 3 for the ones `owned_changed` names |
| `owned_changed` | The owned files whose template text changed since the last setup or update; the repo's copy never gets that change by itself, so the new text waits at `.bindwright/incoming/<path>` | Review it (step 3) |
| `unchanged` | Already up to date | Nothing |
| `skipped` | A staged copy from an earlier run was already there, so the new one was not written; the file keeps its old base | Settle the old copy, then run the update again: it stages the newer text |

When the repo has `.github/workflows/claude-code-review.yml` or `.github/review-checks/bindwright_templates.py` and `advanced.localOnly` is not true, copy `${CLAUDE_PLUGIN_ROOT}/helper.json` over `.bindwright/helper.json` (create it when missing). The CI review jobs read that pin from the PR's base: they install the helper it names, so the attribution guard can read commands there when it ships in the repo, and the template-text check runs a release's engine only when its download matches the pin's hash, so the pin stays at the plugin's version wherever the guard hook lives.

Edits inside `.claude/` ask the user for permission even when edits are otherwise accepted. Before the first one, say that the next steps change the repo's agent settings and rules.

## 3. Settle what was staged

Go through `.bindwright/incoming/` file by file. Delete each staged copy once its file is settled. Then run the engine with `--clean-staging <repo root>`, never `rm -rf`, which the project's settings deny: it removes the folder once no staged copy waits in it, lists the ones that still do under `unsettled`, and refuses a folder that is a link.

- **A `staged` file:** no earlier version exists to merge against, so merge it with the repo's copy the way setup's merge step does: run the engine with `--propose-merge <repo root>` (it lists every file in `.bindwright/incoming/`; use the proposals for the `staged` ones, since a `conflict` file carries its own markers), read each proposal against the repo, and show the summary, the clashes with both versions and a recommendation for each. Save only after a yes. Never replace a `LICENSE` without an explicit yes.
- **A `conflict` file:** the staged copy is the merged file, with each clash marked `<<<<<<< this repo`, `||||||| last setup or update`, `=======` and `>>>>>>> today's templates`. Everything outside the markers already merged cleanly. For each clash, show the user the three versions in plain words (what the repo has, what the templates had, what they have now) and ask which to keep, or write a mix they agree to. Then save the result over the repo's file, with no markers left. When the staged copy has no markers, the clash is a kept section (`bindwright:keep` to `bindwright:end-keep`) that the merge would change: keep the repo's section as it is, and take the rest from the staged copy only on a yes.
- **An `owned_changed` file, or any staged copy whose path `.bindwright/owned` lists:** the project owns it, so the update left it alone, but the templates changed it, and a fix or a new step in that text never reaches the project. The new template text is staged at `.bindwright/incoming/<path>` and waits there through later updates until it is settled, so an update run again first, or a session that ends first, loses nothing. Take this bullet instead of the `staged` one for it: compare the staged text with the project's copy (its `--propose-merge` proposal helps), say in plain words which of the template's changes the project's copy lacks, and carry each one into the project's copy only on a yes, fitted to the project's own wording. When the repo has no file at that path, the project left the template out on purpose, often because another of its files covers the same topic (`.bindwright/owned` may say which): find that file by the staged text's headings or a search for its key sentences, and carry the changes there the same way, on a yes. When no file covers the topic, say that the changes have no home in this project, and leave them out. Delete the staged copy either way once it is settled. On a no the project's copy stays as it is, and the next update does not ask again, since the record already holds the new text.

A settled conflict does not come back: the update already recorded today's templates as the new base, so the next one compares against them.

## 4. Fill and check the new text

Files that were `added`, or merged from new text, can hold placeholders setup fills (`{{TEST_COMMAND}}` and the rest). Search those files for `{{` and fill each placeholder the way setup's step 6 says, reading the repo first and asking only what it cannot answer. Then check that every command and path the new text names exists in the repo. Last, when the `from` that `--releases-since` printed in step 2 is an `x.y.z` version older than its `to`, search the repo's tracked files outside `.bindwright/` for it (FindWright's `search` tool when the session has it, since its search hook refuses a shell search in a repo it indexes; otherwise `git grep -nF "<from>" -- ':!.bindwright'`) and list each hit that names Bindwright's version for the user to update; the update never edits the project's own docs. Skip the search for any other `from`. Likewise, when a file in `.github/workflows/` that the update `updated` or `merged` changed a `uses:` line's pin (the text after `@`), search the tracked files outside `.github/workflows/` and `.bindwright/` for each old pin, the same way (`git grep -nF "<old pin>" -- ':!.github/workflows' ':!.bindwright'` without FindWright) and list each hit for the user to update, since a project doc that records its CI setup names the pin too.

When the repo has the template-text check (`bindwright_templates.py` in the folder `prescreen.dir` names in `.github/review-gate.yml`) and `.github/review-guide.md` has no `## Bindwright template text` heading, the check runs but the reviewer is never told what to do with its list, since the guide is the project's own copy and the merge kept it. Say so, show that section from `<helper>/_core/project-template/.github/review-guide.md.template`, and add it to the guide on a yes. Then, when the guide had that heading already or just gained it, look in the guide and the project's own rules (`CLAUDE.md`, `.claude/rules/`) for a verdict rule the project wrote itself that makes every written finding blocking, such as "any finding written down is 🔴". Bindwright's own verdict rule in `review-tiers.md` already leaves the upstream list out, so it is not that rule; a copy of it the project keeps in `.bindwright/owned` without that exception is. Read that way, it blocks on the upstream list too, so quote it and offer one sentence after it that leaves the findings under "Upstream: Bindwright template text" out of the verdict, saved on a yes. A file listed in `.bindwright/owned` is edited only on that yes, like any other.

When `advanced.tracker` in `.bindwright/project.json` is `github` and the repo root still holds an old hand-off file (`*-CONTEXT_*.md`), say that `/start-session` no longer reads it, since the work state now lives in GitHub issues. Offer to turn its open items, and any in a `ROADMAP.md`, into issues, one at a time, as setup's step 6 does under **Tracker**. Once every open item of the hand-off file is an issue, offer to delete it; on a no, it stays. A `ROADMAP.md` stays either way, since the project may keep one of its own.

## 5. Offer the removals

For each path in `removed`, say in one line what the file was for and delete it only on a yes. Mention the `removed_edited` paths: the templates no longer ship them, and the repo keeps its copy.

When `docs/lazy/README.md` is in `removed_edited`, or `docs/lazy/` holds any file other than that README, the project moved rules there the way older setups described, and `CLAUDE.md` no longer carries the "Rules loaded on demand" pointer that told sessions to read them. Say so, and offer to add that pointer back to `CLAUDE.md` in the project's own words, or to move each rule into `.claude/rules/` with a `paths:` list of the files it is about.

Then check that `.claude/settings.local.json`, the personal file that holds the allow list and this person's own switches, stays out of git. Unless `"localOnly"` is true, run `git check-ignore -q --no-index .claude/settings.local.json`; when it fails, add that path to `.gitignore`. When `git ls-files .claude/settings.local.json` prints it, say the file is committed, so everything in it is in the history, and offer `git rm --cached .claude/settings.local.json`, which stops tracking it and keeps the file on disk. Say that every other clone deletes its copy when it pulls or checks out that commit, as git does for a file a commit removes, so each person copies theirs aside first and puts it back after.

Then, when `~/.claude/settings.json` lists the tasks mod in `env.CLAUDE_CODE_PLUGIN_DIRS` and its `env` does not set `CLAUDE_CODE_ENABLE_TODO_TOOLS` to `"1"`, a setup before 5.2.1 installed it: say that the mod answers Claude Code's task tools, which current models hide without that line, so it does nothing until `"CLAUDE_CODE_ENABLE_TODO_TOOLS": "1"` is added to that `env` block, and that it takes effect at the next start of Claude Code. Do not edit the file.

Then, when Python is there, run `python "<helper>/engine/home.py" style-status "<helper>/_core/global-template/output-styles/straight-talk.md"`. On `"state": "older"`, the installed reply style is an earlier Bindwright copy with no edits of the user's: say what the newer text changes (the plugin's changelog names it), and on a yes run the same command with `update-style`, which replaces only such a copy; it applies from the next session. Say nothing on any other state: `"edited"` means the copy holds the user's own changes, which stay, and `"linked"` means it is a link the user keeps, such as into a dotfiles folder, which stays too.

Then, when `<config>/rules/code-style.md` exists (`<config>` is `CLAUDE_CONFIG_DIR` or `~/.claude`) and its first line is not `---`, an earlier `/bindwright:code-style` wrote it, and every session loads it, code or not. Say so, and on a yes add the `paths:` block that `${CLAUDE_PLUGIN_ROOT}/skills/code-style/SKILL.md` step 6 opens the profile with at the top of the file, changing nothing else, so it loads only when a session reads a code file; it applies from the next session.

Then bring the global hooks current. The helper keeps each hook it has a record of current by itself, but a hook installed before Bindwright kept that record is never moved. When Python is there, run `python "<helper>/engine/home.py" hook-status "<helper>/_core/global-template/hooks"`. Say nothing for a hook it lists with `recorded` true, which the helper already keeps current, or with `linked` true, a link the user keeps, such as into a dotfiles folder, which stays. For each other hook with `matches` true, run `home.py adopt-hook "<helper>/_core/global-template/hooks/<name>"` without asking: it only records the hook, so the helper keeps it current from then on, and leaves its entry in `~/.claude/settings.json` as it is. With `matches` false, the installed copy is older or holds the user's edits: name those hooks, say what the shipped text changes, and that reinstalling also rewrites each one's entry in `~/.claude/settings.json` with setup's flags. On one yes, run `home.py install-hook` with that same path, the Python `home.py find-python` prints and the `--matcher` or `--events`, and `--block-on-failure`, that setup's step 7 gives that hook (`${CLAUDE_PLUGIN_ROOT}/skills/setup/SKILL.md`); before the first guard, give that step's warning about a guard that blocks when it fails. Hooks load at the start of a session, so a reinstalled one applies from the next.

Then bring the installed mods current, since setup copies each mod into `~/.claude/mods/` once and a plugin update alone never reaches that copy. When Python is there, run `python "<helper>/engine/home.py" mod-status "<helper>/_core/global-template/mods/<name>"` for each folder under `<helper>/_core/global-template/mods/`. Say nothing on `missing` (not installed), `current`, or `linked` (a link the user keeps, which stays). For the rest, list in one short block per mod what would change, from its `files`: `add` and `replace` take the new text, `remove` deletes a file the template dropped and the user never edited, `edited` keeps the user's edit and writes the new text beside it as `<file>.new` (an edited file the template dropped just stays). On `unrecorded`, the mod was installed before Bindwright kept a record of what it wrote, so it cannot tell an edit from an older copy: say that every differing file would take the new text except the mod's lists of the user's own entries (such as usage-guard's commands to stop), which show as `edited` and stay. A mod whose `files` is empty has only its record to write: an `unrecorded` one, or an `older` one whose last update stopped part-way. Run `update-mod` for it without asking, adding `--adopt` when it is `unrecorded`. Ask once for all of them, "Update these mods now?", with "Yes" first. On a yes run `update-mod` with the same folder, adding `--adopt` for an `unrecorded` mod, and name every path in `kept`, so the user can compare each with its `.new` copy. Mods load at start-up, so the changes apply after the next restart of Claude Code.

## 6. Skill contracts

When the skill-check mod is installed and `python "<helper>/engine/home.py" project-mods <repo root>` does not list it as off here, run `python "<helper>/engine/home.py" skill-contracts <repo root>`. It builds this project's contracts from the template's example file and the answers in `.bindwright/project.json`, compares them with this repo folder's key in `skill-contracts.json`, and prints the `file`, the `key`, the new `steps`, the key's `current` steps (`null` when it has none) and a `case`. The key's `"_offered"` entry holds the template's steps a no turned down; skill-check never reads it, since it looks a contract up by skill name.

- `same` or `declined`: leave the key as it is.
- `missing` or `differs`: show what changes between `current` and `steps`, and ask. On a yes, run the same command with `accept`, which writes the new steps as the key. On a no, run it with `decline`, which keeps the key's own steps and saves the new ones under its `_offered`, so later runs ask again only once the template's steps change. Both keep every other key in the file.

## 7. Review counts

When Node is there and `node "<helper>/hooks/counts.mjs" status` shows `"share": true` with no entry for this repo root, this repo was set up before sharing was turned on. Ask setup's "What kind of project is this?" question (`${CLAUDE_PLUGIN_ROOT}/skills/setup/SKILL.md`, step 3) with its "leave this project out" option, and its batch question when the history check calls for it, and save the answers the same way.

When the status shows `"share": true` and an entry for this repo root whose `kind` is set, the counts go out after each merge, by the step in `.claude/rules/git.md` § Merging that runs `counts.mjs send`, and at `/start-session`. When `advanced.codeHost` in `.bindwright/project.json` is not `"local"` (a local project merges nothing), `.bindwright/owned` lists `.claude/rules/git.md` and no file in `.claude/rules/` names `counts.mjs`, the repo's own git rules lack that step, so its counts go out only when a session starts fresh, and a long session sends none. Say so, show the bullet from `<helper>/_core/project-template/.claude/rules/git.md` § Merging that starts "Then, when Bindwright's helper is installed", and add it after the repo's own merge steps on a yes.

## 8. Finish

Tell the user, in plain words and grouped by kind (rules, skills, hooks, workflows, docs) rather than file by file: what was updated, what merged, what they settled, what was added or removed, and anything left unsettled in `.bindwright/incoming/`.

When the update added `.github/scripts/pin_check.py` and also pinned an action to a commit (a `uses:` line in `.github/workflows/` that now ends in `@<40-hex sha>`), say that the deep review on that PR cannot check the new pins: a deep review runs the base branch's `claude.yml`, which does not look pins up yet. So put those `uses:` lines back at their tags for this PR, and pin them in a second PR once it merges. Those workflow files keep their old bases too, as the paragraph below on files shipped in a later PR says: run `--keep-base` with their paths, so the next update offers the pins again, and the second PR gets the pinned lines the way that paragraph's later PR gets its file.

Then say that `.bindwright/pristine.json` changed too and belongs in the commit, since the next update merges against it, as does `.bindwright/helper.json` when step 2 wrote it, and that nothing is committed: they can read the changes with `git diff` and commit when happy.

When a changed file will ship in a later PR instead (an edit to `.github/workflows/claude-code-review.yml` goes in a PR of its own, and workflow edits land on the default branch first), the commit that leaves it out keeps its old base: put the file back with `git restore <path>`, or delete it when the update `added` it, since the last commit has no copy to restore, then run the engine with `--keep-base <repo root>`, passing `{"paths": [<path>, ...]}` on standard input. For a file the update `renamed`, put back the old path, delete the new one and pass both. Run it before any other update in this clone, on any branch, since each update replaces the record it reads. Without it, `pristine.json` records the new text as already there, and every later update reads the old copy as the repo's own edit and keeps it. The PR that ships the file later gets its text by running this update again on the branch that file ships from (`main` for a workflow edit) and keeping only that file: put every other path back with `git restore`, `pristine.json` included, and delete any file the run added. The next update finds the shipped file matching the templates and moves its base on; a file the repo had edited itself may come back once as `merged` or `conflict` instead, and its settled text is the one already there (`git rerere`, when turned on, replays it).

Do not commit or push.
